🧑‍🏫 這段是 Grok 直播第一天的實作片段：團隊從零開始，把一個「快閃（pop-up）平台」的網站架起來，一路做部署網頁、挑資料庫、找網址。值得看的是他們怎麼分工：哪些交給 AI bot，哪些還得由人來做。先求能上線、再慢慢補功能的做法，也看得很清楚。

  • 155:11 把「正在做什麼」的描述文件交給 AI 處理，文件已經傳給 Roshion
    ↳ 他們把「我們現在在做什麼」寫成一份說明文件，丟給 AI 讀，讓 AI 接手處理。這份文件已經傳給同事 Roshion。
  • 155:11 提到 Slack 裡應該要加上 cursor bot
    ↳ Slack 是團隊用的聊天工具。講者提到應該把 Cursor（一款 AI 寫程式工具）的 bot 加進 Slack，這樣大家在聊天室就能直接叫它做事。
  • 155:45 把 Lauren 加成 Versell organization 的 owner；repo 已經建好但還是空的，後來 Steve 在大家講話時就讓它上線了
    ↳ 在 Versell（應該是網站託管服務 Vercel）的團隊帳號裡，把 Lauren 設成擁有者。repo 是放程式碼的專案資料夾，剛建好還是空的，Steve 趁大家聊天時讓它上線了。
  • 156:17 目前的平台只有一個 index.html，styles 全部寫成 inline，講者自己也說「非常克難（super scrappy）」
    ↳ 整個網站現在只有一個 index.html 網頁檔。外觀設定（styles）直接寫在每個元素上（inline），沒有另外整理成檔案。能動但很陽春，講者自己都說超克難。
  • 156:17 把 Versell 連到 repo：先授權 Versell、設定 GitHub，再選 popup repo
    ↳ 把 Versell 跟程式碼接起來：先同意 Versell 讀取 GitHub（存放程式碼的平台）上的帳號，再選 popup 這個 repo。接好之後，程式一改，網站就會跟著更新。
  • 157:19 講者正在建兩個 bot：ops bot 和 creative director。creative director 負責命名和高層次的細節
    ↳ 講者在做兩個 AI 助手：ops bot 管營運；creative director（創意總監）負責取名字、定大方向這類決策，不碰技術細節。
  • 157:19 ops bot 負責設定 Slack 這類經營公司的雜事；講者說這些事目前還得由人來做，之後會慢慢往自動化發展
    ↳ ops bot 處理開 Slack、設定各種工具這些開公司的瑣事。講者坦白說目前還是得靠人動手，之後才會一步一步交給 bot 自動做。
  • 158:49 正在連接 Notion
    ↳ 他們正在把 Notion（筆記兼資料整理工具）接進來，讓 AI 和系統可以讀寫裡面的資料。
  • 159:20 main 上已經有 deploy 在跑，只要 push to main 就會部署；但頁面還只是 HTML，沒有實際功能
    ↳ main 是程式碼的正式主線。現在只要把改好的程式推上 main（push），網站就會自動更新，這個動作叫部署（deploy）。不過頁面只是靜態網頁，還不能填表單。
  • 159:50 討論 email 要收在哪裡：Google sheet、Notion database（已設好 notion MCTP）、flat file database；有人擔心 Notion 撐不住所有人的流量
    ↳ 討論訪客留的 email 要存在哪：Google 試算表、Notion 資料庫（相關的 Notion MCTP 已經設好），或單純存成一個檔案（flat file）。有人擔心 Notion 撐不住大量流量。
  • 160:20 請 Steve 把已部署的 landing page 接到 Notion，建一個小的 Notion database 來存 signups
    ↳ landing page 是訪客點進來第一眼看到的介紹頁。請 Steve 把它接上 Notion，開一個小資料庫，把報名的人（signups）存進去。
  • 160:51 同時開始檢視 tech stack 的選擇，決定 host 在 Versell
    ↳ tech stack 指整套技術組合，例如網站放在哪、資料用什麼存。他們開始一項一項檢視，先確定網站託管（host）在 Versell。
  • 161:23 提議直接整合 Planet Scale、用正式資料庫，因為先做快速測試的話之後還得拆掉；接著小改成 Planet Scale Postgress
    ↳ 講者覺得先拿 Notion 臨時頂著，之後還得拆掉重做，不如一開始就接 Planet Scale 這種正式資料庫。後來再小改成它的 Postgres 版本（一種常見的資料庫）。
  • 161:55 付款功能延後處理（payments later），nice to have 的項目先不做；講者對計畫給完 feedback 後，要 Steve 改接 Planet Scale
    ↳ 收款功能先不做，「有也不錯」的功能也先放著，專心把核心做完。講者對計畫給完意見後，請 Steve 改接 Planet Scale。
  • 162:25 提到接下來幾天可能會有 Planet Scale 的來賓
    ↳ 講者提到接下來幾天的直播，可能會有 Planet Scale 的人來當來賓。
  • 162:55 進度回顧：Matt 帶 ops team 寫 company playbook、規劃 go to market motion；landing page 原型只是一些 HTML
    ↳ 進度整理：Matt 帶營運團隊寫公司作業手冊（playbook），並規劃 go to market motion，也就是產品怎麼推出、怎麼找到客人。landing page 還只是雛形網頁。
  • 162:55 方向偏向 pop-up business／pop-up 平台：讓大家更容易辦 pop-up，也可能自己辦；Lauren 負責整合工作，目前在設定資料庫
    ↳ pop-up 指快閃店或快閃活動。方向是做一個讓大家輕鬆辦快閃的平台，他們自己也可能辦。Lauren 負責把各部分串起來，現在正在設定資料庫。
  • 163:27 還缺 domain name；可以交給 creative director，或請 chat 想一些好玩的網域名稱
    ↳ 還沒有 domain name（網域，也就是網址，像 xxx.com）。可以交給 creative director 想，或請直播聊天室的觀眾幫忙想好玩的名字。
  • 164:35 想查 shipbythursday.com 還能不能註冊，可能透過 Burcell 購買，直接綁定到專案
    ↳ 想查 shipbythursday.com（「週四前出貨」）還能不能註冊。能的話可能透過 Burcell（聽起來就是 Versell）買，買完直接綁到專案上。
  • 165:07 下一位來賓無法到場，所以直播會花更多時間在實作上
    ↳ 原本排好的下一位來賓來不了，所以直播會多花時間在現場實作。
  • 165:07 等 Planet Scale credentials 的時候，請 Steve 盡量自己排除阻礙（unblock），先思考 table design、設定 dependencies
    ↳ 資料庫的登入資訊（credentials）還沒拿到前，請 Steve 別乾等：先想資料表怎麼設計（table design，也就是要存哪些欄位），並先裝好需要的套件（dependencies）。
  • 166:08 要 Steve 告訴 Tater 之後改用 cloud agents，也可以建一個 project agent
    ↳ 請 Steve 轉告 Tater，之後改用 cloud agents（在雲端跑、不佔自己電腦的 AI 助手）。也可以另外建一個專門顧這個專案的 project agent。
  • 166:39 Grothbot 很適合 orchestrating bots 和自動化，cursor 的 harness 則很擅長 coding；講者習慣讓它幫忙 spin up cloud agents
    ↳ 講者的分工：Grothbot 擅長指揮多個 bot 協作、做自動化（orchestrating）；Cursor 的 harness（讓 AI 實際動手寫程式的工作環境）擅長寫程式。講者習慣請它開 cloud agents。
  • 166:39 cloud agents 是跑在 cursor harness 上的 agent，本身就具備那些 smarts 和 engineering know-how
    ↳ cloud agents 是跑在 Cursor harness 上的 AI，本身就帶著工程師的判斷和經驗，不用每次從頭教它怎麼寫程式。
