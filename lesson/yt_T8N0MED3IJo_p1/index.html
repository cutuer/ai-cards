🧑‍🏫 這段影片由 Solve Intelligence 的講者從頭說明專利怎麼申請、怎麼審查，再說明為什麼 Claude Code 那種「交代完就讓 AI 自己做」的方式，放到專利工作上行不通。它提供了一個很實用的判斷標準：一件事能不能放手交給 AI，要看你能不能很快確認成果對不對。

  • 00:20 講者 Olly Cobb 是 Solve Intelligence 的創始 AI 工程師
    ↳ 講者 Olly Cobb 是 Solve Intelligence 最早期的 AI 工程師，從一開始就負責把 AI 做進產品裡。
  • 00:20 講者認為最能善用近期 AI 進展的領域，一個是軟體開發，另一個是法律
    ↳ 他認為最近 AI 變強之後，最能直接受惠的行業有兩個：寫程式的軟體開發，以及法律。
  • 00:50 這兩個領域的工作成果價值都非常高，所以用 AI 提升效率的動機很明顯，但 AI 在兩者發揮作用的原因不同
    ↳ 這兩行的成果都很值錢，工程師和律師的時間都很貴，所以大家都想用 AI 省時間。不過 AI 在這兩行幫得上忙的原因不一樣。
  • 00:50 軟體開發受益於模型做複雜、技術性、抽象推理的能力
    ↳ 寫程式需要 AI 會「想」：要能處理複雜、技術性、抽象的邏輯，例如先理解整套系統怎麼運作，再動手修改。
  • 01:20 法律工作受益於模型從數千甚至數百萬份可能相關的文件中翻找，挑出關鍵資訊的能力
    ↳ 法律需要 AI 會「找」：從成千上萬、甚至上百萬份文件裡，挑出真正關鍵的那幾段。
  • 01:20 Solve Intelligence 服務的專利法（patent law）剛好位在這兩種問題的交界
    ↳ 專利法（patent law，規定發明怎麼申請保護、怎麼主張權利的法律）剛好兩種能力都要：既要看懂艱深的技術，也要翻找大量文件。
  • 01:20 專利法中 AI 的潛在價值非常高，因此很清楚地指出要釋放這些價值時，哪些選擇最關鍵
    ↳ 正因為 AI 在專利這行能創造很大的價值，反而更看得清楚：想把這些價值真正做出來，哪些設計決定最關鍵。
  • 01:50 專利的核心是發明人與社會之間的社會契約
    ↳ 專利的本質是一筆交換：發明人把發明公開給社會，社會回報他一段時間的獨家權利。
  • 02:22 發明人要公開說明發明如何運作，國家就授予發明人 20 年的壟斷權，決定誰能製造、使用或販售這項發明
    ↳ 交換條件很具體：把發明怎麼運作寫清楚公開，國家就給你 20 年，由你決定誰可以製造、使用或販售它。
  • 02:22 目的是鼓勵創新，同時確保這些知識最終會進入公共領域（public domain）
    ↳ 這樣設計是兩邊都顧：給發明人創新的誘因，時間到了知識就進入公共領域（public domain，大家都能自由使用的知識）。
  • 02:52 取得專利的要件之一：這項發明先前不能在世界任何地方已為公眾所知
    ↳ 條件一是「新」：申請之前，這項發明在全世界任何地方都不能已經公開過。
  • 02:52 要件：必須非顯而易見（non-obvious），也就是對「具有通常知識者」來說不是顯而易見的
    ↳ 條件二是非顯而易見（non-obvious）：就算是新的，如果內行人一看就想得到，也拿不到專利。
  • 02:52 「具有通常知識者」是假想的從業者：具備相關領域專業、讀過相關先前技術，但不會自己發揮創造性想像
    ↳ 「具有通常知識者」是法律上假想的人：懂這一行、讀過既有技術，但不會自己發揮創意。拿他當尺，判斷發明是不是「理所當然的下一步」。
  • 03:22 要件：必須有用，專利局才值得花時間審查並核准
    ↳ 條件三是「有用」：發明要有實際用途，專利局才值得花人力審查、核准。
  • 03:22 要件：必須充分揭露，理論上具有通常知識者只要看申請書的揭露內容，就能重現這項發明
    ↳ 條件四是充分揭露（sufficiently disclosed）：申請書要寫得夠清楚，讓內行人照著做就能做出來，不能藏起關鍵步驟。
  • 03:22 專利申請書包含：一組請求項（claims）、說明書、相關的線條圖式，以及摘要
    ↳ 申請書有四個部分：請求項（claims，列出你要保護什麼）、說明書（詳細解釋發明）、線條圖，以及摘要（abstract，簡短介紹）。
  • 03:53 請求項定義法律上的保護範圍，是專利的核心
    ↳ 請求項最重要，它劃出法律上的「地界」：別人的東西有沒有踩進你的範圍，就看這裡怎麼寫。
  • 03:53 請求項用非常特定的語法撰寫，並設計不同範圍，萬一最廣的版本日後被挑戰，還有退守的位置
    ↳ 請求項有固定寫法，而且會準備寬窄不同的版本：最寬的版本日後如果被推翻，還有較窄的版本可以守住。
  • 04:23 每個請求項的每一個要素，都必須在說明書和圖式中找得到支持
    ↳ 請求項裡的每一個要素，都必須在說明書和圖裡找得到對應的說明，不能主張沒寫出來的東西。
  • 04:23 化學專利還需要正式的結構表示，生技專利還需要明確的序列表
    ↳ 有些領域還有額外格式：化學專利要附正式的化學結構表示，生技專利要附序列表（sequence listings，例如 DNA 或蛋白質序列）。
  • 04:56 提出申請後會進入審查程序（prosecution），這是和專利局之間長達數年的往來對話
    ↳ 送出申請後會進入審查程序（prosecution）：不是交件後等結果，而是和專利局來回溝通好幾年。
  • 04:56 審查委員通常是相關領域的專家，會拿請求項和先前技術比對，並發出審查意見通知（office action）指出問題
    ↳ 審查委員（examiner）通常是該領域的專家，會拿請求項和先前技術（prior art，申請前就已存在的技術）比對，再用審查意見通知（office action）指出問題。
  • 04:56 常見問題例如：請求項不具新穎性、看起來顯而易見，或揭露不夠充分
    ↳ 常被挑出的問題有：已經有人做過（不具新穎性）、內行人想得到（顯而易見），或寫得不夠清楚，別人照著做不出來。
  • 05:28 撰寫人可以反駁審查委員的見解，或修改請求項回應，修改通常代表把範圍縮小
    ↳ 申請方可以反駁、說明審查委員哪裡看錯，也可以修改請求項來過關；但修改通常就是縮小範圍，能保護的東西變少。
  • 05:28 這個過程可能來回好幾輪，撰寫人提出的每個論點都會進入永久紀錄「審查歷程（file history）」
    ↳ 這樣可能來回好幾輪，申請方講過的每一個論點都會留在審查歷程（file history）裡，成為永久紀錄。
  • 05:28 專利核准後，審查歷程會影響日後如何解釋請求項
    ↳ 這份紀錄日後會有影響：專利核准後，別人會拿你當初在審查中說過的話，來解讀請求項的範圍，所以說出口的話要負責。
  • 05:58 專利核准後可以對侵權者行使權利；侵權是指另一個產品或流程符合至少一個請求項的每一個要素
    ↳ 核准後就能向侵權者（infringer）主張權利。判斷方式是：對方的產品或流程只要完整符合某一個請求項的所有要素，就算侵權。
  • 05:58 所以律師通常會把請求項寫得越廣越好，也就是用越少要素越好，但仍要避開先前技術並在說明書中找得到支持
    ↳ 所以律師會想把請求項寫寬：要素越少，別人越容易踩到。但不能寬到跟先前技術重疊，也要在說明書裡有根據。
  • 05:58 專利日後也可能在訴訟中被挑戰，理由是它當初根本不該被核准
    ↳ 拿到專利也不代表從此安全：日後打官司時，對方可以主張這張專利當初根本不該被核准。
  • 06:31 撰寫與審查過程中做的所有決定，後果可能要到很多年後才會顯現
    ↳ 撰寫和審查時的每個取捨，可能要等很多年後，專利被審、被繞過或被告時，才知道當初做得對不對。
  • 06:31 整理律師的工作：第一步，先理解發明人提出的高度技術性發明
    ↳ 律師工作的第一步：先搞懂發明人帶來的東西，這通常是很艱深的技術內容。
  • 07:03 第二步，退一步看，找出這項發明相對於所有先前技術，技術上到底有什麼新穎之處（如果有的話）
    ↳ 第二步：退一步，拿它和所有既有技術比對，找出真正新在哪裡；也可能發現其實沒有新東西。
  • 07:03 第三步，用專利特有的語法寫成法律文件來呈現這份新穎性，並預先考慮日後的駁回和訴訟
    ↳ 第三步：用專利特有的寫法，把這個「新」寫成法律文件，同時預先想好將來可能被駁回、被告的情況。
  • 07:03 專利工作同時用到 LLM 的深度技術推理，以及「大海撈針」的能力
    ↳ 所以專利工作同時需要 LLM（大型語言模型，像 Claude 這類 AI）的兩種能力：深入的技術推理，以及在大量文件中大海撈針。
  • 07:33 對不訓練模型、而是在模型上開發產品的人來說，關鍵問題是應用層（application layer）能不能帶來實質價值
    ↳ 對不自己訓練模型、而是拿現成模型做產品的公司來說，關鍵問題是應用層（application layer，建在模型之上的那層產品）能不能真的帶來價值。
  • 08:05 換句話說：值得專門為專利律師開發軟體嗎？還是他們直接用 co-work 或其他不分領域的通用工具就好？
    ↳ 換句話說：值得專門為專利律師開發一套軟體嗎？還是律師直接用 co-work 這類不分領域（domain agnostic）的通用 AI 工具就夠了？
  • 08:35 講者希望這些分析有些能推廣，幫大家思考自己的領域該做什麼、怎麼做，甚至找出值得投入的領域
    ↳ 講者希望這套分析不只適用於專利，也能幫大家想清楚自己的行業該做什麼、怎麼做，甚至找出值得投入的方向。
  • 08:35 講者以軟體開發當參照，因為大多數人都知道 Claude Code 在開發軟體上有多成功
    ↳ 他拿軟體開發當對照，因為大家都知道 Claude Code（Anthropic 給工程師用、能自己寫程式和改程式的 AI 工具）很成功。
  • 09:05 co-work 可以看成是 Claude Code 背後模式的通用化版本，這個模式就是委派（delegation）
    ↳ co-work 可以看成把 Claude Code 那套做法搬到一般工作上，而這套做法的核心叫委派（delegation）。
  • 09:05 委派的意思是：你描述想要什麼，再把實作交給 agent
    ↳ 委派的意思是：你只講想要什麼結果，實際怎麼做交給 agent（能自己規劃步驟、動手執行的 AI）。
  • 09:05 講者要說明為什麼委派模式不適合專利工作，並強調前兩個理由最根本、也最可能適用到其他領域
    ↳ 講者要說明委派為什麼不適合專利工作，並說前兩個理由最根本，也最可能套用到其他行業。
  • 09:35 第一個理由：專利撰寫的產出不像軟體那樣容易驗證
    ↳ 第一個理由：專利寫得好不好，沒辦法像程式那樣很快檢查出來。
  • 09:35 軟體開發中很多東西可以用測試驗證，其餘的也常常花幾分鐘 QA 就能驗證
    ↳ 寫程式時，很多部分可以跑自動測試確認對錯；測不到的部分，花幾分鐘 QA（實際操作、檢查品質）通常也能確認。
  • 09:35 所以軟體可以用高層次描述需求，讓 agent 長時間自主執行，再快速、低成本地驗證結果
    ↳ 所以寫程式可以只交代大方向，讓 agent 自己跑很久，最後再用又快又便宜的方式檢查成果。
  • 10:07 軟體結果有錯，可以調整 prompt 再試一次，直到正確為止
    ↳ 結果錯了也沒關係，改一下給 AI 的指令（prompt）再跑一次，反覆試到對為止。
  • 10:07 相比之下，專利沒辦法「執行」，它對不對取決於尚未發生的事
    ↳ 專利就不同了：它不是能按下去「執行」看結果的東西，寫得好不好，要看未來還沒發生的事。
  • 10:38 例如：審查委員兩年後可能提出什麼駁回、競爭對手五年後可能怎麼迴避設計、訴訟律師十年後可能怎麼讓專利無效
    ↳ 例如兩年後審查委員會怎麼駁回、五年後競爭對手會怎麼繞過專利設計產品、十年後對方律師會怎麼讓專利無效，這些現在都無法驗證。
📘 術語
patent（專利）：發明人與社會之間的社會契約：公開說明發明，換取 20 年壟斷權
patent law（專利法）：講者說它位在深度技術推理和大量文件搜尋這兩種問題的交界
public domain（公共領域）：專利制度確保知識最終會進入的地方
non-obvious（非顯而易見性）：發明對具有通常知識者來說不能是顯而易見的
person having ordinary skill in the art（具有通常知識者）：假想的從業者：有相關專業、讀過先前技術，但不會自己發揮創造性想像
prior art（先前技術）：審查時拿來和請求項比對的既有技術；請求項必須避開它
sufficiently disclosed（充分揭露）：具有通常知識者應該能照申請書的揭露內容重現發明
claims（請求項）：定義法律保護範圍，是專利的核心，用特定語法撰寫
abstract（摘要）：專利申請書的組成部分之一
sequence listings（序列表）：生技專利額外需要提供的明確資料
prosecution（專利審查程序）：提出申請後和專利局長達數年的往來對話
examiner（審查委員）：通常是相關領域專家，拿請求項和先前技術比對
office action（審查意見通知）：審查委員發出的通知，指出不具新穎性、顯而易見等問題
file history（審查歷程）：撰寫人所有論點形成的永久紀錄，影響日後怎麼解釋請求項
infringer（侵權者）：產品或流程符合至少一個請求項每一個要素的人
application layer（應用層）：在模型之上開發產品的那一層；問題是它能不能增加實質價值
domain agnostic（不分領域的通用工具）：例如 co-work 這類不是專為某個領域打造的方案
delegation（委派）：描述想要什麼，把實作交給 agent；講者說這是 Claude Code 和 co-work 的模式
QA（品質檢查）：軟體開發中，測試以外還能花幾分鐘驗證產出的方法
