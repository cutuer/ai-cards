🧑‍🏫 這是 Grok 官方 Bot Galaxy 直播第一天中的一段。講者分享怎麼讓 bot 少花錢、分工更聰明，也回答了現場提問，包括怎麼開始設定、怎麼讓 AI 照規則做決定、怎麼搬移舊工具的設定。如果你已經在用 bot 自動做事，卻覺得費用高、成效普通，這段的建議馬上就能用。

  • 477:29 很多人高估 routine 需要執行的頻率，例如每 15 分鐘跑一次，換算下來一天約 100 次，是很貴的 routine
    ↳ 「routine」是讓 bot 定時自動做的例行任務。很多人設成每 15 分鐘跑一次，一天就將近 100 次，每次都要花錢，其實多半用不到這麼頻繁。
  • 477:29 真的需要 routine 時，改用 webhook 或某種 inbound signal 觸發，讓 bot 收到輸入後才執行，不要照 schedule 盲目執行
    ↳ 與其定時空跑，不如有事才叫它做。「webhook」是別的服務一有新動靜就主動通知 bot 的機制，算是一種「inbound signal」（外部傳進來的觸發訊號）。收到通知才開工，比定時空跑省。
  • 477:59 光是少跑幾次、改用觸發式這兩件事，大概就能省下不少 token
    ↳ 「token」是 AI 計算用量的單位，用得越多越花錢。只要把執行頻率降下來，改成有事才觸發，光這兩步就能省下不少費用。
  • 477:59 做一個 voice bot，也就是模仿你聲音的 bot；講者認為這是把想法傳遞給別人最被低估的方法
    ↳ 「voice bot」是用你的聲音說話的 bot。講者認為，用你自己的聲音把想法傳達給別人，是目前最被低估的方式，會這樣用的人很少。
  • 477:59 匯入你的 cookies：讓 bot 在許多工具上保持登入，也不用一直接管 bot 的電腦幫它處理
    ↳ 「cookies」是瀏覽器用來記住你登入狀態的小檔案。把它交給 bot，它就能用你的身分登入各種工具，不會一直卡在登入畫面，你也不用親自到它的電腦上幫忙處理。
  • 478:31 依專長把 bot 分組（講者說這是個人偏好）：擅長處理客戶的 bot 負責所有客戶相關事務，擅長資料分析的 bot 只做資料分析
    ↳ 講者習慣讓每個 bot 專做一類事：跟客戶有關的全部交給客戶 bot，數據分析只交給分析 bot，不讓同一個 bot 什麼都做。他也說這是個人偏好。
  • 478:31 原因是會發生一些我們不知道的複利效應；即使兩個任務看似完全不同，只要屬於同一專長，仍能獲得複利好處
    ↳ 理由是同類工作做久了會累積經驗，產生一些說不太清楚的「複利」好處。就算兩件事表面上完全不同，只要屬於同一個專長，bot 就會越做越上手。
  • 479:01 其他技巧還有 great skills（bot 能從你身上學習）以及 auto optimization routines
    ↳ 還有兩個技巧：「skills」是 bot 從你的做事方式學到、可以重複使用的能力；「auto optimization routines」是讓 bot 定期自動改善自己做法的例行任務。
  • 479:01 講者認為很重要的一點：設一個專門優化其他 bot 的 bot，負責改善 routine、找出哪裡出錯、哪裡你得重複要求，並避免再發生
    ↳ 講者特別強調：專門設一個「優化 bot」，負責檢查其他 bot 的例行任務，找出哪裡出錯、哪些要求你老是得重講，然後修好，讓同樣的問題不再發生。
  • 479:01 讓這個 bot 監督並改善其他 bot，比自己做容易得多；設定一次就不用管，講者覺得這麼做的人還不夠多
    ↳ 自己一個一個盯 bot 很累，交給優化 bot 去監督就輕鬆多了，而且只要設定一次就能一直運作。講者覺得這樣做的人還太少。
  • 479:31 講者留下 Stockbot 的 QR code 讓大家拿去用，鼓勵大家試試看
    ↳ 講者現場秀出 Stockbot 的 QR code（手機一掃就能打開的條碼），讓大家直接拿去用，鼓勵觀眾自己動手試試看。
  • 480:01 講者認為這些 bot 最酷的地方在於能多有創意；founder 最適合去探索它的邊界，目前還沒碰到極限
    ↳ 講者覺得這些 bot 最酷的是能玩出很多創意用法。「founder」（創業者）最適合去試它的能耐到哪裡，目前大家都還沒碰到它的上限。
  • 481:01 Q&A：怎麼設定 bot？第一步是弄清楚你需要它們做什麼：把你要做的每件事都盤點出來，再把這些事分組
    ↳ 問答：怎麼開始設定 bot？先別急著開 bot，先把自己平常要做的事全部列出來，再把性質相近的事分成幾組。
  • 481:31 講者讓每個 bot 成為某個特定領域的專家，有領域外的問題時再擴大範圍，例如 finance bot、客戶 bot、行銷 bot
    ↳ 講者讓每個 bot 只當某一個領域的專家，例如財務 bot、客戶 bot、行銷 bot。遇到超出範圍的問題時，才再擴大它負責的內容。
  • 481:31 有人喜歡由一個 chief of staff bot 管理其他 bot；講者自己不愛用，但認為這是個人偏好
    ↳ 「chief of staff bot」就像幕僚長，負責指揮、分派工作給其他 bot。有人喜歡這樣管，講者自己不愛，但他說這純粹看個人習慣。
  • 482:02 想把工作都抽象化、只跟一個 bot 對話就用 chief of staff bot；喜歡深入細節掌控的人，適合用多個專家 bot 並加以訓練
    ↳ 怎麼選？如果你只想對一個窗口交代事情、不想管細節，就用幕僚長 bot；如果你喜歡自己掌控每個環節，就養多個專家 bot，再分別訓練它們。
  • 482:32 Q&A：多台電腦管理 bot？大約一週前 bot 在多台電腦間容易混亂，團隊正在積極改善，現在應該好很多，有問題可以找他們聊
    ↳ 問答：bot 分散在好幾台電腦上要怎麼管？大約一週前這樣很容易亂掉，團隊正在積極修，現在應該好很多了。還有問題可以直接找團隊反映。
  • 482:32 講者提到有很多人以前用其他方案，排了一整排 Mac mini，想要全部利用起來
    ↳ 講者提到，很多人以前用別的方案，排了一整排 Mac mini（蘋果的小型桌機），現在想讓這些機器全部派上用場。
  • 483:32 Q&A：企業如何讓決策遵守確定性規則？模型本身不是確定性的，最簡單的解法是讓模型寫 code，因為 code 本身是確定性的
    ↳ 問答：企業決策要照規則走怎麼辦？「deterministic（確定性）」是指同樣的輸入一定得到同樣的結果。AI 每次回答可能不一樣，程式碼不會，所以最簡單的做法是讓模型把規則寫成程式。
  • 483:32 做法：用 cloud agents 寫 code 並給它一個決策樹，再告訴模型每次需要時都呼叫那個 function
    ↳ 做法是用「cloud agents」（在雲端執行的 AI 助手）把「decision tree」（一層層是非題組成的判斷流程）寫成一段程式，再規定 bot 每次需要做這類決定時都要執行它。
  • 484:02 也可以讓 bot 向其他 bot 請求許可，但講者認為更好的方式是給規則：每次做相關決策都要看這張流程圖再執行
    ↳ 另一種做法是讓 bot 做決定前先問另一個 bot 同不同意。不過講者更推薦直接給規則：每次做這類決策，都先看這張「flowchart」（流程圖），照著走。
  • 484:02 只要有可驗證的 code 可執行，bot 就能「cosplay」成確定性的樣子
    ↳ 重點是：只要背後有一段可以驗證結果的程式能執行，bot 本身雖然不固定，也能「cosplay」（假扮）成每次結果都一樣的樣子。
  • 485:03 Q&A：如何從其他工具匯入設定？一，正在做，講者有個 bot 預計幾天內分享，會讓這件事容易很多
    ↳ 問答：怎麼把其他工具的設定搬過來？第一，團隊正在做這件事。講者自己也有一個 bot，預計幾天內分享出來，到時候會容易很多。
  • 485:03 二，確保所有連線可互通：你已有的 MCP 和 API 目前可能分散在許多工具裡
    ↳ 第二，讓所有連線都能互通。「API」是軟體之間交換資料的接口，「MCP」是讓 AI 連接外部工具的標準做法。你現有的這些連線，可能散落在好幾個工具裡。
  • 485:34 整合的方式跟處理 agents 和 skills 一樣：用 symlink 或建立一個直接的 source of truth 來統一管理
    ↳ 整合方法跟整理 agents、skills 一樣：用「symlink」（捷徑，讓不同位置都指向同一份檔案），或設一個「source of truth」（唯一的正本），所有工具都從這裡讀設定。
  • 485:34 Linux 比較困難，但可以用一些整合，例如 one password：把東西都匯入後再用它的 MCP，它能處理得很好
    ↳ Linux 系統處理起來比較麻煩，可以借助 1Password 這類整合（密碼管理工具）：先把帳號密碼都匯進去，再讓 bot 透過它的 MCP 取用，效果不錯。
  • 485:34 另一個方法是 cookies：從 Chrome 或瀏覽器匯入所有 cookies，然後在 bot 裡直接使用那些 session
    ↳ 另一招是從 Chrome 等瀏覽器匯出所有 cookies 給 bot，bot 就能直接沿用你已經登入的「session」（登入中的狀態），不用重新登入。
  • 486:05 還有部分驗證問題在解決中；也有公司不想讓 bot 上他們的平台，團隊目標是當好的生態系成員，這是整個生態系的共同挑戰
    ↳ 有些登入驗證的問題還在處理。也有公司不希望 bot 進入他們的平台，團隊想當守規矩的一份子，這是整個 AI 生態系都要面對的難題。

    ↳ 問答：驗證工具卡關怎麼辦？要看你的設定。講者建議，使用 Grockbot 最好的方法之一是讓它自己想辦法，不要硬性規定它一定要用哪個工具。
  • 487:11 講者最後選用 Granola，不是因為很喜歡它，而是它最方便讓 Grockbot 抓逐字稿、給出洞察，特別是在裝置上發生的事
    ↳ 例如講者最後用了 Granola（會議筆記工具）。不是因為特別喜歡它，而是它最方便讓 Grockbot 抓逐字稿、整理出重點，尤其是裝置上發生的事。

    ↳ 這個選擇之後可能會變：如果某個工具推出「first party integration」（官方直接內建的串接），講者的優化 bot 可能會自己發現，然後改用它。

    ↳ 現在還在早期，很多事要自己想辦法變通。希望之後「marketplace」（外掛商店）上的「plugin」（外掛）越來越多，最後能支援各種工具的需求。
  • 488:43 Q&A：舊系統沒有 API 或 API 比 UI 貴，怎麼讓走 UI 流程跟 API 一樣快？講者說有兩件事有幫助
    ↳ 問答：舊系統沒有 API，或走 API 比操作畫面還貴，要怎麼讓 bot 操作「UI」（使用者介面，就是一般人點的畫面）時跟 API 一樣快？講者說有兩件事有幫助。
  • 489:15 第一是盡量走 headless：用 headless browser 快速完成工作，就不用操作 UI（字幕在此中斷）
    ↳ 第一是盡量用「headless browser」，也就是沒有畫面、在背景直接執行的瀏覽器，bot 不用一步步點畫面，速度快很多。（字幕在這裡中斷，第二點沒錄到。）
📘 術語
routine（例行排程任務）：讓 bot 按排程執行的任務，跑太頻繁會很貴
webhook（網路回呼）：建議用來觸發 routine，取代照 schedule 盲目執行
inbound signal（輸入訊號）：讓 bot 收到輸入後才執行 routine 的觸發訊號
token（權杖（用量單位））：減少 routine 次數、改用觸發式可以省下 token
voice bot（語音 bot）：模仿你聲音的 bot
cookies（瀏覽器 cookie）：匯入後 bot 可在多個工具保持登入，不用一直接管它的電腦
chief of staff bot（幕僚長 bot）：管理其他 bot 的 bot，讓你只需跟一個 bot 對話
deterministic（確定性）：模型本身不是確定性的，code 才是；靠執行 code 讓 bot 表現得像確定性
decision tree / flowchart（決策樹／流程圖）：給 bot 的規則，每次做相關決策都照著執行
cloud agents（雲端 agent）：用來寫 code 以處理確定性部分
MCP（MCP）：和 API 一樣是你用來連接工具的方式，目前可能分散在各工具中
symlink（符號連結）：跟處理 agents、skills 一樣，用來把分散的連線整合到同一來源
source of truth（單一真實來源）：統一管理所有連線的直接來源
first party integration（官方原生整合）：之後出現時，優化 bot 可能改用它取代原本的工具
headless browser（無頭瀏覽器）：用來快速完成工作、不用操作 UI 的瀏覽器
