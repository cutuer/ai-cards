🧑‍🏫 這段影片先是 xAI 的 Grokbot 開放試用的現場。Grokbot 是可以替你動手做事的 AI 助理。後半段由 xAI 內部負責營運的人示範他們平常怎麼用它。最值得看的是一個觀念：不是工程師，也能用 AI 自己做出工具，不必只發規定叫別人照做。

  • 23:51 團隊準備開放 Grokbot 讓大家試用，使用者的回饋會送進他們自建的 automated feature factory 來改進產品
    ↳ 團隊要把 Grokbot 開放給大家試用。大家的意見會送進他們自建的 automated feature factory，這是一套把使用者回饋轉成產品改進的系統。所以用的人越多，產品改得越快。
  • 23:51 現場出錯：用 X 帳號登入（login with X）有問題，團隊說接下來一小時要處理
    ↳ 現場馬上出狀況：login with X（用 X 帳號直接登入、不用另外註冊）的功能壞了。團隊說接下來一小時內會修好，看得出產品才剛開放，還在邊跑邊修。
  • 24:24 講者的除錯做法：看到錯誤就去查 server 端發生什麼事，再把狀況交給 Grokbot；也可以直接叫 Grokbot 自己去打開來看
    ↳ 講者的除錯方式很直接：一看到錯誤，就去查 server 端（在背後跑服務的主機）出了什麼事，再把狀況交給 Grokbot 處理。也可以直接叫 Grokbot 自己打開來查。
  • 30:41 能交給 Grokbot 做的工作幾乎沒有限制，講者認為隨著模型進步會越來越是這樣
    ↳ 講者認為，能交給 Grokbot 的工作幾乎沒有上限，而且模型越進步，這句話就越成立。這是他個人的判斷，不代表現在每件事它都做得好。
  • 30:41 Grokbot 的 agent 是 always-on：不必因為怕 agent 停下來就不敢闔上筆電
    ↳ agent 是會自己動手執行任務的 AI。always-on 是說它一直在運作：你闔上筆電、下班回家，它還在繼續做，不用守在電腦前等它做完。
  • 31:15 把這些 primitives 組合起來後，就能自然地跟 bot 對話、清楚知道它們有哪些權限，而且它們能全天候工作，產出高價值成果
    ↳ primitives 影片沒有明確定義，可以先理解成幾個基本的功能模組。把它們組合起來後，你可以用平常說話的方式指揮 bot，清楚知道它能動哪些東西，還能讓它全天候幫你做事。
  • 31:46 講者要分享 xAI 內部 RevOps 和 MarOps 團隊怎麼用 Grokbot 提升工作效率，並請現場做 RevOps、MarOps、GTM engineering／GTM systems 的人舉手
    ↳ 接著講 xAI 內部的用法。RevOps（營收營運）和 MarOps（行銷營運）負責業務、行銷背後的流程和工具。GTM engineering/systems 是替產品上市推廣建系統的人。講者先請這些人舉手。
  • 32:21 如果只能挑一點講：有了 Grokbot，終於可以「做工具，而不只是訂規則」
    ↳ 講者說，如果只能帶走一個重點，就是這句：以前營運人員只能「訂規則」要別人遵守，有了 Grokbot，他們可以自己「做工具」，把規則直接做進工具裡。
  • 32:21 這類跨部門協作、要協調利害關係人的職位，很多時間都花在溝通、發布資訊，然後希望大家照著指引做（例如活動怎麼設定、怎麼追蹤）
    ↳ 這類工作要協調很多部門和相關的人，大部分時間花在溝通、發公告，然後只能希望大家照做。像是行銷活動該怎麼設定、成效該怎麼追蹤，做不做全看對方。
  • 32:54 有了 Grokbot，大家可以把自己當成更技術的角色：不再只是發一份 checklist 要其他團隊照做，而是直接建好基礎設施，例如內部 app
    ↳ 意思是不會寫程式的營運人員，也能像技術人員一樣做事。不再只是發一份 checklist 叫大家照著勾，而是直接用 Grokbot 做出公司內部自己用的 app 給大家用。
  • 33:24 這些 app 一開始就設計成會遵守規則；可以把行銷和業務團隊想成在玩一個由後勤 ops 團隊設計的遊戲
    ↳ 這些 app 一開始就把規則寫進去，照著畫面操作，自然就符合規定。講者的比喻是：業務和行銷在玩一個遊戲，規則是後勤營運團隊設計的，玩家不用背規則。
