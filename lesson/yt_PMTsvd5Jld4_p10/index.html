🧑‍🏫 這段是 Grok 直播第一天，主持群一邊聊「用 AI 工作就像玩策略遊戲」，一邊當場叫 bot 發想餐廳快閃店的點子。值得看的地方是整個過程都攤開來：先問需求、給回饋、再分工，接著直接做原型。這就是他們平常用 AI 做事的真實流程。

  • 107:26 有種說法：喜歡 Age of Empires、Factorio、Starcraft 這類遊戲的人，特別擅長使用 agents
    ↳ 有人說，愛玩《世紀帝國》《Factorio》《星海爭霸》這類策略遊戲的人特別會用 agent（能自己完成任務的 AI 助手），因為兩者都要會分派、會指揮。
  • 108:27 有人說 AI 的終極介面是語音，但講者認為其實是「玩遊戲」，另一位講者也同意
    ↳ 很多人以為跟 AI 互動，最後會變成直接用講的。講者覺得更像打電動：看局面、下指令、看結果再調整，另一位講者也同意。
  • 108:27 早期 PM 工作是寫很長的 brief、列出所有需求再去做；現在比較像遊戲化：對 bot 下 prompt，由 bot 撰寫或創作，人變成 orchestrator
    ↳ PM（產品經理）以前要先寫一大份 brief（需求說明）才開工。現在是對 bot 下 prompt（給 AI 的指令），讓它去寫去做，人當 orchestrator（總指揮）負責分派和把關。
  • 109:28 講者在 SpaceX Slack 上的狀態一直都是「why not today?」。他形容輸入框很神奇，打什麼 agent 都能做到，像在施咒，幾乎每件事都只差一個 prompt
    ↳ Slack 是公司內部的聊天工具。講者的狀態一直掛著「why not today?（何不今天就做）」。他覺得輸入框打一句 agent 就會做，像施咒，很多事只差一句 prompt。
  • 109:58 講者會挑戰自己：與其開 issue，不如直接開 PR 或叫 bot 去修
    ↳ 工程師發現問題，常開 issue（問題回報單）等別人處理；PR 是直接交出改好的程式碼，請人審核合併。講者逼自己跳過回報這一步，直接修，或叫 bot 去修。
  • 109:58 與其寫很詳細的 PRD，不如直接帶 prototype 給團隊，大家對著可點擊、可互動的東西討論，更視覺化也更真實
    ↳ PRD（產品需求文件）是寫滿規格的文件；prototype（原型）是能點、能操作的初版。講者覺得拿實物給大家邊點邊討論，比讀文件更直觀，也更容易發現問題。
  • 110:28 活動只有三天。講者請 bot 發想「neighborhood restaurant ops assistant」（社區餐廳營運助理），想用真實世界的經營者驗證 bot
    ↳ 活動只有三天。講者請 bot 發想一個「社區餐廳營運助理」，想找真實的店家來用，看看 bot 在現實工作裡到底管不管用。
  • 110:58 講者認為程式碼相對便宜、能快速做出東西的時代，仍要清楚掌握 user stories，所以先請 bot 列出 user stories
    ↳ user stories（使用者故事）是用「誰想做什麼、為什麼」來描述需求。講者認為就算現在寫程式又快又便宜，還是要先搞清楚要幫誰解決什麼，所以先叫 bot 列出來。
  • 110:58 bot 有抓到任務重點，還主動提議幾個第一天就能做的 demo，可以先做幾個 prototype 看看感覺
    ↳ bot 有抓到這次任務的重點，還主動提議幾個第一天就能做的 demo（示範版），建議先做幾個原型，實際看看感覺對不對。
  • 111:28 bot 提的例子：餐廳營運經理每天早上一份簡報（訂位、菜單上有／沒有的品項）、老闆管理評論平台上的評論
    ↳ bot 舉的情境：每天早上給餐廳經理一份簡報，列出當天訂位、哪些菜有供應、哪些沒有；或是幫老闆管理評論網站上的客人評論。
  • 111:28 其他例子：幫人處理家務或每週的麻煩事（例如找承包商）、幫小型組織協調公益團體，或讓志工協調人管理團隊
    ↳ 其他情境還有：幫一般人處理家務或每週的麻煩事，例如找修繕師傅；幫小型組織協調公益團體；或幫志工負責人管理團隊。
  • 111:58 講者想在灣區做實體、面對面的專案，把科技和真實有形的東西連起來，但也承認從直播間做到很難
    ↳ 講者想在灣區（舊金山一帶）做實體、面對面的專案，讓科技連上看得到、摸得到的東西。但他也承認，人在直播間很難做到。
  • 112:28 講者對 bot 的訊息按愛心後，bot 就沿著這方向繼續做，還主動提了名稱，例如 Open Brief、Kitchen Desk
    ↳ 講者對 bot 某則訊息按了愛心，bot 就知道這個方向對了，順著往下做，還主動想了產品名稱，例如 Open Brief、Kitchen Desk。
  • 113:00 對訊息按愛心，Grok bot 會知道並把它納入後續回覆。講者另外建了一個 market research bot；bot 也有 templates 可以分享給別人
    ↳ 在 Grok bot 按愛心就是給回饋，它會把這個納入後續回覆。講者另外建了一個做市場調查的 bot；templates（範本）能把設定好的 bot 分享給別人直接套用。
  • 113:30 直播時打字不方便，可以按按鈕用語音輸入。講者用語音請 bot 發想結合實體元素的餐廳商業點子
    ↳ 直播時邊講邊打字不方便，可以按按鈕改用語音輸入。講者就用講的，請 bot 想一些結合實體元素的餐廳生意點子。
  • 114:01 兩個客群：想開新餐廳、先用 pop-up 試水溫的人（setup 角度）；已經有餐廳、想經營得更有效率的人（ops 角度）
    ↳ 點子鎖定兩種人：一種想開新店，先用 pop-up（限期的快閃店）試水溫，需要的是開店籌備；另一種已經有店，想經營得更有效率，需要的是日常營運。
  • 114:01 講者當場加入 X connector，之前 plugins 一個都沒接，全部現場設定
    ↳ connector（連接器）讓 bot 接上外部服務。講者當場接上 X（前身是推特），之後就能透過它聊天、操作。plugins（外掛）他原本一個都沒接，全部現場設定。
  • 114:31 bot 點子一：Pop-up OS for restaurants。這是一個 pop-up studio，幫在地餐廳推出限期的概念店，現場把作業系統做出來，由真正的主廚當客戶
    ↳ 點子一「餐廳快閃店作業系統」：成立一個工作室，幫在地餐廳推出限期的概念店，把背後的管理系統當場做出來，並請真正的主廚當客戶。
  • 114:31 bot 點子二：adopt a restaurant，幫助經營困難的舊金山店家
    ↳ 點子二「認養一家餐廳」：鎖定舊金山經營困難的店家，幫他們一把。
  • 115:01 bot 點子三：experiential dinner theater／售票制 supper club。講者喜歡售票這部分，很多活動都需要售票和管理報名者
    ↳ 點子三：體驗式晚餐劇場，或售票制的 supper club（事先預約、付費入場的餐會）。講者最喜歡售票這部分，因為很多活動都需要賣票和管理報名名單。
  • 115:01 bot 點子四：由 bot 幫參加者預訂餐桌。講者也說有些回覆是「典型 AI 回覆」
    ↳ 點子四：讓 bot 幫參加者訂位。講者也直說，有些回覆就是「典型 AI 回覆」，聽起來合理但沒新意，要自己判斷好壞。
  • 115:01 bot 建議的最佳組合：Pop-up OS 加一家真實的舊金山餐廳。做後端系統、找場地、主廚和合作餐廳辦活動，達成出產品、幫老闆、辦一場讓人品嚐或取餐的活動
    ↳ bot 建議的最佳組合：快閃店系統配一家真的舊金山餐廳。做後台、找場地、主廚和合作餐廳辦活動，一次做到產品上線、幫到老闆、讓人真的吃到東西。
  • 116:02 從工程角度看，辦 pop-up 很複雜，需要活動管理、金流、報名系統等
    ↳ 從工程角度看，辦快閃店很複雜，要處理活動管理、收款、報名系統等好幾塊，缺一塊都辦不起來。
  • 116:32 訂位要考慮：時段（例如 4:00–5:00、4:30–5:30）、場地座位配置、能容納多少人、要電話訂位還是線上訂位（或兩者都要）
    ↳ 光是訂位就很多細節：時段怎麼切（例如 4:00–5:00 或 4:30–5:30）、座位怎麼排、最多坐幾人、接電話訂還是網路訂，或兩種都要。
  • 116:32 有人提議直接開始做 prototype，實際看、摸所有東西；例如做一個舊金山愛店的 pop-up landing page，甚至辦在 Dreamforce 附近
    ↳ 有人提議別再空想，直接做原型來看、來摸。例如替一家舊金山愛店做快閃活動的 landing page（活動介紹網頁），甚至辦在 Dreamforce（舊金山的大型科技年會）附近。

    ↳ go-to-market（把產品推向市場）要專人負責，可以用 go-to-market bot 或 prospecting bot（找潛在客戶的 bot），後者應該能在 marketplace（bot 商店）找到。
  • 117:35 要做的事：找會做菜的人或餐廳、找想吃的客人、處理 pop-up 物流；這些都得聯絡真人，所以需要 bot 去對外聯繫
    ↳ 要做的事：找會做菜的人或餐廳、找想來吃的客人、處理快閃店的物流。這些都要聯絡真人，所以需要一個專門對外聯繫的 bot。
  • 118:36 分工：一位講者先在 Notion 做 brain dump；Lauren 負責 prototype；Peter 協助釐清方向
    ↳ 當場分工：一位講者先在 Notion（筆記協作工具）把腦中想法全倒出來；Lauren 負責做原型；Peter 協助釐清方向。

    ↳ 做原型時可以直接新開一個專用 bot，取名 prototyping bot，用 Cursor（用 AI 協助寫程式的編輯器）做出活動網頁的原型。

📘 術語
agent（代理人／AI 代理）：住在電腦裡的「alien intelligence」，輸入框打什麼它都能做到
orchestrator（指揮者／協調者）：對 bot 下 prompt、讓 bot 撰寫或創作，人負責指揮調度
PR (pull request)（合併請求）：講者說與其開 issue，不如直接開 PR 或叫 bot 修
PRD（產品需求文件）：詳細的產品規格；講者建議改用 prototype 取代
prototype（原型）：可點擊、可互動的東西，讓團隊對著實物討論
user stories（使用者故事）：講者認為在程式碼便宜的時代，仍要清楚掌握的需求描述
connector（連接器）：例如講者現場加入 X connector，就能透過它聊天操作
plugins（外掛）：字幕只提到直播前一個都沒接
templates（範本）：bot 的範本，可以分享給別人使用
marketplace（市集）：可以找到現成 bot（例如 prospecting bot）的地方
prospecting bot（開發潛在客戶的 bot）：用於 go-to-market，對外聯絡真人
go-to-market（市場推廣）：例如聯絡在地店家等對外推廣的流程
pop-up（快閃店）：限期推出的餐廳概念店，可以讓想開餐廳的人先試水溫
landing page（登陸頁）：打算用 Cursor 做的 prototype，讓觀眾可以去看
