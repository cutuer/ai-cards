🧑‍🏫 這支影片由負責行銷營運的 Ian 示範，他怎麼用 Claude Cowork（Claude 直接幫你處理檔案、跑多步驟工作的模式）完成每週的指標檢討。值得看的地方在於分工：撈資料和核對數字交給 Claude，這週要講什麼、怎麼講由人決定，而且整套做法可以每週重複使用，也能交給同事。

  • 00:10 講者 Ian 負責 marketing ops 和分析，工作是用數據幫行銷團隊把行銷做得更好
    ↳ 講者 Ian 做的是 marketing ops（行銷營運）。他不直接做廣告活動，而是整理、分析數據，讓行銷團隊知道哪裡做得好、哪裡要調整。
  • 00:10 他每週要做一份 metrics review：給行銷團隊一份完整細節的文件，再給主管一張一頁的摘要投影片
    ↳ 他每週要交一份 metrics review（指標檢討）。同一批數據要做成兩個版本：詳細文件給行銷同事看細節，一頁投影片給主管快速看重點。
  • 00:10 以前這件事要從大約六個不同地方撈資料
    ↳ 以前光是把資料湊齊，就要到大約六個不同的地方去撈，再自己整理對齊。這段最花時間的工作，正是他想交給 Claude 的部分。
  • 00:10 用 Claude Cowork 之後，他把這週的資料（字幕原文為 contacts）丟進去，由 Claude 驗證資料，他自己負責掌握敘事方向
    ↳ 用了 Cowork 之後分工就變了。他把這週的資料交給 Claude，核對數字的苦工由 Claude 做，他專心想「這週要說一個什麼樣的故事」。
  • 00:10 整個流程靠 connectors 和 skills 來跑
    ↳ 整個流程靠兩樣東西跑。connectors 一般是指讓 Claude 連上其他工具拿資料的功能，影片沒有細講；skills 是寫好的做事步驟，後面會說明。
  • 00:10 總共用了三個 skill：一個準備檢討內容，一個校對，一個管理待辦事項（action items）
    ↳ 他做了三個 skill，各負責一段：一個準備檢討內容，一個校對，一個管 action items，也就是會後誰要做什麼的待辦清單。
  • 00:41 這些 skill 把流程固定下來，所以每週都能用同一套方式跑，也能把流程分享給團隊
    ↳ skill 的價值是把做法固定下來。步驟和規則都寫好，每週照同一套跑，不必靠記憶；也能直接交給同事，大家的做法就會一致。
  • 00:41 每週日晚上會跑一個 scheduled task，讀取上週的檢討和會議逐字稿
    ↳ 他設了一個 scheduled task（排程任務，時間到就自動執行）。每週日晚上會自動讀上週的檢討和會議逐字稿，先把背景資料補齊。
  • 00:41 這個 scheduled task 也會到 Slack 看業務團隊目前的重點，並查詢資料倉儲（warehouse）
    ↳ 這個排程也會去 Slack（常見的工作聊天軟體）看業務團隊最近的重點，再查資料倉儲（warehouse，公司集中存放數據的地方）。
  • 00:41 跑完後，Claude 會留一個資料夾給他，裡面有數字和幾個建議的關注重點
    ↳ 跑完後，Claude 會留一個資料夾給他，裡面有整理好的數字，還有幾個「這週可能值得關注」的建議，等他來看。
  • 01:12 週一早上他打開 Cowork 問 Claude 準備得怎麼樣，重點摘要和建議的關注方向都已經準備好了
    ↳ 所以週一早上他不用從零開始。打開 Cowork 問一句「準備得怎樣」，重點摘要和建議的方向就已經擺在眼前了。
  • 01:12 Claude 很會撈數字，但決定敘事方向和這週要聚焦什麼，還是要由人來判斷
    ↳ 他在這裡劃了一條線：撈數字是 Claude 的強項，但這週要強調什麼、故事怎麼講，還是要懂公司狀況的人來決定。
  • 01:12 每週的焦點不一樣：有時要回應業務的優先事項，有時是產品上市；這週剛好碰到換季，所以聚焦在 Q2 計畫
    ↳ 每週的重點都不一樣，有時要配合業務的優先事項，有時碰上產品上市。這週剛好換季，所以他把焦點放在 Q2 的計畫。
  • 01:42 他把季度檢討文件（QBR doc）丟給 Claude，並告訴 Claude 要先講什麼
    ↳ 他把 QBR doc（季度檢討文件）交給 Claude，並講清楚要先講哪個部分，等於先幫報告定好開場和順序。
  • 01:42 prep skill 有一條規則：資料對不上時，Claude 會標出來並提問，不會自己猜答案
    ↳ prep skill（負責準備內容的那個 skill）有一條規則：數字對不上時要標出來問人，不能自己猜。這樣錯誤才不會被悄悄蓋過去。
  • 01:42 例子：業務團隊做了小規模的組織調整，行銷的報表跟他們對不上了；Claude 列出落差、問他怎麼處理，他決定照業務團隊的版本
    ↳ 舉例來說，業務團隊做了小規模的 reorg（組織調整），兩邊的報表就對不上了。Claude 列出落差來問他，他決定照業務的版本。
  • 02:12 proofreading skill 會檢查草稿裡的每個數字，確認都能追溯回已驗證的資料來源，讓他對報告內容有信心
    ↳ proofreading skill（校對用的 skill）會逐一檢查草稿裡的每個數字，確認都查得回驗證過的資料來源，他交出去才放心。
  • 02:12 第一版草稿只有指標表格和標題，先確認大綱沒問題再往下填內容
    ↳ 第一版草稿故意做得很簡單，只有指標表格和各段標題。先確認大綱方向對了再寫內容，免得整篇寫完才發現要重來。
  • 02:12 標題確認後他請 Claude 展開；prep skill 會讓 Claude 補上支撐細節和例子，但已經同意的標題一字不改
    ↳ 標題確認後，他才請 Claude 補上細節和例子。規則要求已經同意的標題一字不改，避免 Claude 自作主張改掉他定好的基調。
  • 02:43 全部確認沒問題後他說 ship it，Claude 就會把團隊在檢討會前要讀的文件定稿，並幫團隊頻道寫好 Slack 訊息
    ↳ 全部確認後他說 ship it（意思是「可以發了」），Claude 就把團隊會前要讀的文件定稿，並寫好要貼到團隊 Slack 頻道的訊息。
  • 02:43 後續要跟進的事項都會建成任務（字幕原文為 a sauna task），確保不會漏掉
    ↳ 要後續跟進的事項會建成任務，確保不會漏掉。字幕寫成 a sauna task，發音很像任務管理工具 Asana，但影片沒有明講。
  • 02:43 最後，Claude 用同一份資料和敘事做出給主管的投影片，內容是：什麼變了、為什麼變、該怎麼做
    ↳ 最後給主管的投影片，用的是同一份資料、同一套說法，濃縮成三件事：什麼變了、為什麼變、接下來該怎麼做。
  • 02:43 收尾時他會問 Claude：這週的流程學到了什麼，哪些應該寫進 skill 給下週用
    ↳ 收尾時他會再問 Claude：這週的流程學到了什麼、哪些該寫進 skill？也就是每週做完就順手檢討做法，讓下週更順。
  • 03:13 新的業務團隊架構和他做過的修正都會存下來，Claude 會更新 skill
    ↳ 業務團隊的新架構和他這週做過的修正都會存下來，Claude 會拿來更新 skill，下週就不用再為同一件事卡住。
  • 03:13 因為做成了 skill，就能分享給團隊，任何人來跑都能得到一樣的結果
    ↳ 流程寫成 skill 之後就能分享給同事，換誰來跑都會得到一樣的結果，不會因為某個人請假就沒人能做。
📘 術語
marketing ops（行銷營運）：講者的工作：用數據幫助行銷團隊把行銷做得更好
metrics review（指標檢討）：每週產出的東西：給行銷團隊的完整文件，加上給主管的一頁摘要投影片
connectors（連接器）：字幕只說他的流程靠 connectors 和 skills 來跑，沒有進一步解釋
skill（技能）：把流程固定下來，讓每週都能照同一套方式跑，還能分享給團隊；可以隨時更新
scheduled task（排程任務）：每週日晚上自動執行，讀上週檢討、會議逐字稿，看 Slack 並查資料倉儲
warehouse（資料倉儲）：scheduled task 會去查詢的資料來源，字幕沒有進一步解釋
QBR doc（季度檢討文件）：字幕把它稱作 quarterly review doc，也就是季度檢討文件
reorg（組織調整）：業務團隊做了小規模的組織調整，導致雙方報表對不上
action items（待辦事項）：其中一個 skill 專門用來管理這些事項
