🧑‍🏫 這段直播前半，講者用 Grockbot 現場開發一個「找場地」的工具，也宣布了直播挑戰賽。後半開始一場演講，由 SpaceX AI 產品團隊的講者說明產品經理（PM）怎麼用 Grockbot。值得看的地方是它說清楚了一個轉變：AI 不再只是回答問題的聊天視窗，而是會像同事一樣，進到不同工具裡把事情做完。

  • 346:15 場地規劃改了方向：改成辦藝術快閃（art popup），不做餐飲體驗，接下來以大型倉庫空間為優先
    ↳ 他們在幫一場活動找場地，現在改成辦藝術快閃（art popup，只開放一小段時間的臨時藝術展），不辦餐飲。所以找場地時，會先看大型倉庫這類空間。
  • 346:15 自己手動做的場地研究可以拿來驗證工具：如果工具得出的結論跟人自己的判斷一樣，就代表工具有用
    ↳ 講者之前自己手動查過一輪場地，這份結果可以當成對照組。工具找出來的場地如果跟人的判斷差不多，就能相信這個工具真的有用。
  • 346:45 搜尋功能不用重新造輪子，直接用 Google Maps API，再往上加幾層，依更具體的條件篩選
    ↳ API 是讓程式直接跟別的服務要資料的接口。搜尋場地直接用 Google Maps 現成的資料，不用自己從零做起，再往上加篩選條件，縮小到真正符合需求的地點。
  • 347:16 場地大小這類資訊 Google Maps 大概查不到，所以可能得自己蒐集資料
    ↳ 但像場地有多大這種細節，Google Maps 通常查不到。這部分可能要自己打電話問，或另外蒐集資料。
  • 347:16 構想：打完電話拿到細節後，把資料輸入系統（類似 CRM），讓 venue finder 越用越聰明，累積場地和聯絡人的資訊
    ↳ CRM 是用來管理客戶和聯絡人的系統。構想是每打一通電話問到細節，就記進系統裡。venue finder（他們在做的找場地工具）累積的資料越多，就越會找場地。
  • 347:46 目前先手動記下來，之後再試著串接進系統
    ↳ 自動記錄進系統的功能還沒做好，所以現在先手動記下來，之後再試著把它串進系統。
  • 347:46 文件（docs）已經上線，正在持續更新
    ↳ docs 是這個專案的說明文件。現在已經公開，還在一邊做一邊補內容。
  • 347:46 講者的「mini factory」已經在跑：engineer bot 正常運作，verifier bot 忙著 review PR
    ↳ mini factory 是講者讓幾個 bot 分工合作的小產線。engineer bot 正常運作中，verifier bot 在忙著 review PR。PR 是「把改好的程式併進正式版本」的申請，review 就是審核這份申請。
  • 348:17 這些 PR 缺少影片和截圖，講者想要有這些才看得到做出了什麼；接下來交給 Steve 負責完成
    ↳ 講者希望每個 PR 都附上操作影片或截圖，這樣不用讀程式碼，也看得到到底改了什麼。補上這些的工作交給 Steve 負責。
  • 348:17 用 Resend 處理 email：有人登記 wait list 時，會從 hello at ship by Thursday 寄確認信，資料也會照樣進資料庫
    ↳ Resend 是專門幫程式寄 email 的服務。有人登記 wait list（想搶先試用的人留下資料的候補名單）時，系統會從 hello at ship by Thursday 寄出確認信，資料也照樣存進資料庫。
  • 348:47 正在更新部分文案（copy），很快就會 merge
    ↳ copy 指網頁上的文字內容。merge 是把改好的版本正式併進去，所以這些修改過的文字很快就會出現在正式版本裡。
  • 350:17 Grok Galaxy 直播挑戰：投稿 Grockbot 的 template，最有創意的 template 獲勝
    ↳ 直播辦了挑戰賽。template 是做好的範本，別人拿去就能直接套用。大家投稿自己做的 Grockbot 範本，最有創意的人獲勝。
  • 350:47 獎品：得主和一位同伴（plus one）去德州 Starbase 看 Starship 發射，得主很快就會公布
    ↳ Starbase 是 SpaceX 在德州的基地，Starship 是 SpaceX 的大型火箭。得主可以帶一個同伴（plus one）去現場看發射，得主很快就會公布。
  • 351:49 PR 和 agent 數量很多，講者把它們依狀態（status）分組，檢查各個 agent 在做什麼
    ↳ agent 是會自己動手完成任務的 AI，不只是回答問題。講者同時開了很多 agent，手上也有很多 PR，所以依狀態分組，一個一個看各自在做什麼。
  • 353:08 開始預先腦力激盪，覺得需要一個類似「project」的概念給使用者用
    ↳ 講者先想下一步：使用者可能需要類似「專案（project）」的東西，把同一件事相關的內容收在一起管理。
  • 354:12 演講開始：「Grockbot for product managers」，講者是 SpaceX AI 產品團隊的 Kevin Dearco 和 Roshan Sani
    ↳ PM（product manager，產品經理）負責決定產品要做什麼。這場演講教 PM 怎麼用 Grockbot，講者是 SpaceX AI 產品團隊的 Kevin Dearco 和 Roshan Sani。
  • 354:12 演講內容：分享他們用 Grockbot 開發的方式，以及覺得很好用的技巧、工具和 bot
    ↳ 他們會分享自己平常怎麼用 Grockbot 做產品，還有實際用過、覺得好用的技巧、工具和 bot。
  • 354:42 背景：做軟體這門功夫正在快速改變，寫程式、做東西、做 prototype 變得比以往都容易上手
    ↳ 前提是：現在寫程式、做 prototype（先做出一個能試用的雛型）比以前簡單很多，不是工程師的人也做得到。
  • 354:42 引用 Ruby on Rails 作者之一 DHH 的話：「Software is product management」——要做什麼、為誰做、怎麼做、長什麼樣、優先順序是什麼
    ↳ DHH 是網站開發框架 Ruby on Rails 的作者之一。他說「做軟體就是做產品管理」，意思是真正難的是決定做什麼、給誰用、怎麼做、長什麼樣、先做哪個。
  • 355:12 不管原本是工程師、設計師、創辦人還是 PM，只要幫客戶或使用者做軟體，都得面對這些問題
    ↳ 意思是：程式變好寫之後，不管你原本是什麼角色，只要在做給別人用的軟體，都得面對這些產品決策，等於每個人都要有 PM 的思考方式。
  • 355:42 Grockbot 本身也是一個產品，背後有它被做出來的故事
    ↳ 接著他們把 Grockbot 本身當成例子，講這個產品是從什麼需求開始，一路被做出來的。
  • 355:42 起因：SpaceX 內部很多人開始覺得光用 chat box 不夠了，感覺 agent 待在 chat box 裡並不自在
    ↳ chat box 就是一問一答的聊天視窗。SpaceX 內部很多人開始覺得，只讓 AI 待在聊天視窗裡，能做的事太有限。
  • 356:13 使用方式從「要一段回覆、等文字」變成「請 agent 推動成果」；這種以成果為導向的做法先在 coding agent 上大量出現
    ↳ 以前是問一句、等 AI 回一段文字；現在是交代一個目標，讓 agent 自己做到完成。coding agent（幫忙寫程式的 AI）最早開始大量這樣用。
  • 356:13 當內部開始把這種做法用到寫程式以外的地方，就覺得 chat box 有點綁手綁腳，於是開始探索讓 agent 完成任務、存取各種系統的方式
    ↳ 當內部想把這種做法用到寫程式以外的工作，就發現聊天視窗綁手綁腳，於是開始研究怎麼讓 agent 連上各種系統、把任務做完。
  • 356:44 大家討論時最常出現的想法：把 agent 當同事，例如坐在旁邊、可以在 Slack 傳訊息、能看 Linear 的 ticket、一起在 Notion 寫 PRD
    ↳ 大家最常想到的是把 agent 當同事：坐在你旁邊、能在 Slack（公司聊天工具）傳訊息、看 Linear 上的 ticket（待辦工作單）、在 Notion 一起寫 PRD（產品需求文件）。
  • 357:14 Grockbot 會發展成今天的樣子，核心理念就是要有能一起做產品的「agentic 同事」
    ↳ Grockbot 會長成現在這樣，核心想法就是做出「agentic 同事」：一個會主動做事、能跟你一起把產品做出來的 AI 夥伴，而不是只會回答問題的工具。
  • 357:14 根據「同事」的定義，他們整理出四點方向；第一點：同事會把多個工具串在一起，在很多系統之間工作，不會只待在一個系統裡
    ↳ 他們從「同事是什麼樣子」整理出四個方向。第一個是：同事會在好幾個工具之間來回、把工作串起來，不會只待在一個系統裡。
  • 357:45 系統的例子：ticket 系統（Linear、Jira）、CRM（例如 Salesforce）、文件放 Notion、設計放 Figma；每個工具在各自的用途上都很強
    ↳ 例如 Linear、Jira 管待辦工作，Salesforce 是常見的 CRM，Notion 放文件，Figma 做設計稿。每個工具各有專長，所以 agent 也得能跨工具工作。
📘 術語
PR (pull request)（合併請求）：字幕沒有解釋，只提到 verifier bot 在 review PR，而且這些 PR 缺影片和截圖
CRM（客戶關係管理系統）：字幕用來形容打電話後把場地、聯絡人資料記進系統的做法；也舉 Salesforce 當例子
Google Maps API（Google 地圖 API）：用來做搜尋功能，不用重新造輪子，再加幾層篩選條件
venue finder（場地搜尋工具）：他們在做的工具，構想是越用越聰明、越用越會找場地
engineer bot / verifier bot（工程師 bot／驗證 bot）：講者 mini factory 裡的 bot；verifier bot 負責 review PR
wait list（候補名單）：有人登記時會收到確認信，資料會進資料庫
template（範本）：直播挑戰要大家投稿 Grockbot 的 template，最有創意的獲勝
chat box（聊天框）：講者認為 agent 待在 chat box 裡不自在，用在寫程式以外的地方時有點受限
coding agent（寫程式的 agent）：以成果為導向的 agent 用法最先大量出現在這裡
PRD（產品需求文件）：字幕沒有解釋，只舉例可以和 agent 一起在 Notion 寫 PRD
