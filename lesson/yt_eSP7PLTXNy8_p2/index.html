🧑‍🏫 這支是影片後半段，講怎麼把 Claude Code 的 routine 設計得好用。routine 就是讓 Claude 按時間或遇到某件事時自動開工的設定。影片講三件事：要給 Claude 哪些資料、怎麼盯住它的品質，還有兩個實機示範和幾個工作上的真實用法。想讓 AI 不用等你開口就自己做事的人，很值得看。

  • 11:04 設定 routine 時可以給 session 更多情境，例如接上 Google Drive connector，讓 Claude 讀現有的行銷簡報，沿用對外文宣的用語
    ↳ 設定 routine 時可以接上 connector，也就是讓 Claude 連到外部服務的通道，例如 Google Drive。Claude 先讀過公司的行銷簡報，寫文件時就會沿用對外宣傳的說法。
  • 11:34 可以接上 Slack connector，讓 Claude 每次建立 PR 時在 Slack 通知你
    ↳ Slack 是很多公司用的工作聊天軟體。PR 是向程式碼庫提出的一份修改申請，要有人審過才會併進去。接上 Slack 之後，Claude 每次開好 PR 都會傳訊息通知你。
  • 11:34 設定 routine 時要想清楚給哪些情境：Claude 擁有的情境，就是它能做到多好的上限
    ↳ Claude 再聰明，也只能根據你給它看的東西做事。資料給得少，成果就有天花板。想要它做得好，先想清楚它需要看到什麼。
  • 11:34 最後要考慮的是 steerability（可引導性）：怎麼確保 Claude 的產出品質，有幾種做法
    ↳ steerability 字面是「可操控性」，這裡是指你有哪些辦法確保 Claude 自動做出來的東西品質不走鐘。影片接下來介紹三種做法。
  • 12:05 做法一：agent-on-agent review，借用多 agent 系統裡的 generator–critiquer 模式
    ↳ 第一招是讓 AI 審 AI。agent 是指能自己一步步完成任務的 AI。這招借用多個 agent 分工的做法：一個負責產出，一個負責挑毛病，就像寫稿和校稿分開。
  • 12:05 例如一個 routine 負責建立文件 PR，另一個 routine 在 PR 建立時觸發，搶在人類看之前先在 PR 上留評論
    ↳ 實際做法是：A routine 改好文件並開 PR，「PR 建立」這件事會自動叫醒 B routine 來審，在人打開之前先留下意見。等人來看時，已經先過一輪把關。
  • 12:36 做法二：雖然人不在迴圈裡很方便，但有時仍需要監看 session，把 Claude 導向別的方向
    ↳ 第二招是人自己盯著。全自動雖然省事，但 Claude 有時會走偏，所以你還是要能看到它在做什麼，必要時把它拉回來。
  • 12:36 在 Claude Code on the web 可以即時觀看進行中的 session，就像在終端機跟 Claude 合作；可以中途提問、改變方向
    ↳ Claude Code on the web 是網頁版的 Claude Code。session 是 Claude 的一次工作過程，網頁上可以即時看它做，隨時插話提問或叫它改方向，跟在終端機（打指令的視窗）裡和它合作一樣。
  • 12:36 也可以接續過去的 routine 或 session，繼續原本的對話
    ↳ 自動跑完的工作不是做完就結束。之後還能打開當時的對話接著聊，例如追問它為什麼這樣改，或請它補做。
  • 13:07 做法三：驗證 Claude 的產出。以文件為例，會把 Claude 修改或新增的文件頁面實際渲染出來，確認結果符合預期
    ↳ 第三招是驗收成果，不能只聽 Claude 說它做了什麼。以文件為例，要把它改過或新增的頁面實際顯示出來看一次，確認內容和排版都對。
  • 13:39 Demo：在 Claude.ai 左側面板點 Code 按鈕，進入 Routines，打開先前建立的 routine
    ↳ 實機示範開始：在 Claude.ai 網站左邊選單點「Code」，再進到 Routines 頁面，就能打開之前建好的 routine。
  • 13:39 這個 routine 連了兩個 repo：模擬的 Claude Code 原始碼，以及 Claude Code 文件
    ↳ repo（程式碼庫）是存放一個專案所有檔案和修改紀錄的地方。這個 routine 同時能看兩個 repo：一個是模擬的 Claude Code 程式，一個是它的說明文件。
  • 14:09 排程是每週一上午 10:00 執行，並連接 GitHub 和 Slack
    ↳ 它設定成每週一早上十點自動執行，並接上 GitHub（存放程式碼、開 PR 的平台）和 Slack，這樣才能開 PR、發通知。
  • 14:09 右側的指示是 Claude 根據一開始貼上的 prompt 和使用者回答的問題產生的，內容是 Claude Code fork 的每週文件同步
    ↳ 右邊的工作說明不是講者自己寫的：他貼上一段需求，回答 Claude 反問的幾個問題，Claude 再整理成指示。內容是每週幫一份 fork（從原專案複製出來的版本）同步文件。
  • 14:41 點進 session 可以看到，這些指示會在 Claude Code session 一開始就貼進去
    ↳ 點開其中一次執行可以看到，這份指示就是 Claude 開工時收到的第一段話。所以每次都是從同一份工作說明書開始。
  • 14:41 Claude 先看原始碼 repo 的變更、最近 merge 的 PR 和 change log，再跟文件 repo 比對，找到落差後自動開 PR
    ↳ 流程是：先看程式最近改了什麼、有哪些 PR 被 merge（正式併入）、change log（更新紀錄）寫了什麼，再對照文件哪裡沒跟上，發現落差就自己開 PR 補上。
  • 15:11 第二個示範：用 GitHub 事件觸發 routine，每次建立新 GitHub issue 就執行
    ↳ 第二個示範改成「有事發生才啟動」：只要 GitHub 上有人開新的 issue（回報問題或提需求的單子），routine 就會自動開工。
  • 15:41 指示內容：調查觸發的 issue，判斷是不是文件缺口；如果是，就開 PR 並在指定頻道通知
    ↳ 它收到的指示是：先看懂這張 issue 在講什麼，判斷是不是文件漏寫了東西。如果是，就開 PR 補上，並在指定的 Slack 頻道通知大家。
  • 16:11 觸發分兩種：排程觸發、事件觸發；事件觸發支援原生 GitHub 事件，也能從自己的程式碼送 POST request 來觸發
    ↳ trigger（觸發）就是叫醒 routine 的方式，分成定時和有事發生兩種。事件除了 GitHub 內建的，也能讓自己的程式送一個 POST request（透過網路傳過去的「開始」訊號）來啟動。
  • 16:11 設定 GitHub 事件觸發：在 Claude Code 文件 repo 有 issue 開啟時觸發，並連接 Slack 和 GitHub
    ↳ 設定方式：觸發條件選「Claude Code 文件 repo 有人開 issue 時」，再接上 Slack 和 GitHub。
  • 16:44 實測：在文件 repo 建立一個 issue，內容是新版本的文件漏掉幾個工具
    ↳ 講者實際測試：在文件 repo 開一張 issue，寫說新版本的文件漏掉了幾個工具。
  • 17:14 重新整理頁面就看到新的執行；一開始的指示是第一個 prompt，issue 的內容也一起傳進去
    ↳ 重新整理頁面，就多了一次新的執行。第一段話是事先寫好的指示，issue 的內容也一起帶進去，所以 Claude 知道這次要處理哪一張單。
  • 17:14 因為已經有另一個 PR 在處理，講者直接告訴 Claude 停止這個 session，示範 routine 啟動後可以即時引導
    ↳ 因為同一個問題已經有別的 PR 在處理，講者直接叫 Claude 停下來。重點是：routine 自動跑起來以後，你還是隨時能介入、改方向或叫停。
  • 18:17 案例一 deploy verifier：服務剛部署完，確認服務健康、判斷要不要 rollback
    ↳ 案例一「部署驗證員」：deploy（部署）是把新版程式放上線。上線後讓 Claude 檢查服務有沒有正常運作，判斷要不要 rollback（撤回這次更新、退回舊版）。
  • 18:17 設計 routine 要想三件事：用什麼觸發、給什麼情境、怎麼互動或引導讓 Claude 保持誠實
    ↳ 設計 routine 時要回答三個問題：什麼時候叫它開工、給它看哪些資料、你怎麼跟它互動和把關，讓它老實回報、不亂講。
  • 18:47 觸發：CD pipeline 每次部署後可以 POST 到 routines 支援的 webhook，啟動 Claude Code session
    ↳ CD pipeline 是程式改好後自動測試、自動上線的流水線。每次上線完，讓它送訊號到 routine 的 webhook（專門接收通知的網址），Claude 就會開始檢查。
  • 18:47 情境：給 Claude 剛部署服務的原始碼
    ↳ 要讓 Claude 看得到剛上線那個服務的程式碼，它才知道這次改了什麼、可能在哪裡出錯。
  • 19:18 情境：給監控工具（例如 DataDog、Grafana）；出問題時透過 Slack、email，甚至 Twilio 簡訊通知
    ↳ 也要接上 DataDog、Grafana 這類監控工具，看錯誤率、回應速度等數據。一發現異常，就透過 Slack、email，甚至 Twilio（發簡訊的服務）通知人。
  • 19:49 引導：先讓 Claude 調查並給出 go／no-go 的 rollback 建議，在 Claude Code on the web 閱讀它的分析，再視情況請它協助 rollback
    ↳ 一開始先不讓 Claude 直接動手：請它調查後給出「要不要退版」的建議。你在網頁上讀完它的分析，覺得合理，再請它幫忙退版。
  • 20:19 越來越信任 Claude 的判斷之後，可以讓它依監控資料自行 rollback
    ↳ 等你看過夠多次、確定它判斷可靠，再放手讓它根據監控數據自己決定、自己退版。對它的信任是一步步累積的。
  • 20:19 其他案例：on-call investigator（值班調查員）
    ↳ 另一個案例是 on-call investigator。on-call 指輪到值班、系統出事要第一時間處理的人。這個 routine 會先替值班的人查出問題在哪。
  • 20:19 PM 案例：每週用時間觸發一個 job，讀 GitHub issues 或 Slack 頻道裡的待辦項目，協助排優先順序，並為最重要的項目開 PR
    ↳ PM（產品經理）的用法：每週固定跑一次，整理 GitHub issue 或 Slack 頻道裡的待辦事項，幫忙排優先順序，並替最重要的幾項先開 PR。
  • 20:50 結論：主動式 agent 勝過被動式 agent，讓 Claude 從工具變成隊友，自己回應問題、自己開 PR
    ↳ proactive agent（主動式 agent）不用等人下指令，事情發生就自己處理、自己開 PR。講者認為這樣 Claude 就不只是工具，而是會主動接球的隊友。
  • 21:22 打造 routines 是為了讓你不用維護基礎設施，可以專注在自己的領域和流程專業
    ↳ 做 routines 是為了讓你不用自己架伺服器、寫排程系統，這些底層的東西交給平台處理，你專心在自己最懂的工作和流程上。
  • 21:22 在 Claude Code 裡只要一個 /schedule 指令，就能建立你的第一個 routine
    ↳ 在 Claude Code 裡輸入 /schedule 這個指令，就能開始建立你的第一個 routine。
📘 術語
routine（例行任務）：可以按排程或事件自動啟動 Claude Code session 的設定
connector（連接器）：讓 Claude 在 session 中存取 Google Drive、Slack 等外部服務
steerability（可引導性）：怎麼確保 Claude 產出的品質，包括審查、即時引導和驗證
agent-on-agent review（agent 互相審查）：一個 routine 產出 PR，另一個 routine 在人類之前先留評論
generator critiquer pattern（生成者–評論者模式）：多 agent 系統的設計模式，這裡借來做 agent 互相審查
Claude Code on the web（網頁版 Claude Code）：可以即時看 session、中途提問或改方向，也能接續過去的 session
trigger（觸發條件）：啟動 routine 的方式，分成排程觸發和事件觸發
webhook / POST request（webhook／POST 請求）：從自己的程式碼（例如 CD pipeline）送 POST 來觸發 routine
deploy verifier（部署驗證器）：部署後確認服務是否健康、要不要 rollback 的 routine 案例
roll back（回滾）：撤回剛部署的變更
CD pipeline（持續部署流程）：每次部署後可以 POST 到 webhook，當成 routine 的觸發條件
proactive agent（主動式 agent）：不用等人按 Enter，自己回應問題並開 PR 的 agent
