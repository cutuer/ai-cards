🧑‍🏫 這段影片介紹 Claude Code 的幾項新功能：可以在桌面版 app 直接看 Claude 寫的計畫和改過的程式碼，也能在上面留言；另外還有 auto mode、worktree、auto memory 和 code review 四個功能。它們要解決的問題很類似：讓 Claude 自己跑久一點，少一點停下來等你，而且記得你是怎麼做事的。如果你常覺得要一直盯著 Claude、一直按同意、一直重講同樣的事，這段值得看。

  • 10:44 用 plan mode 產生逐步實作計畫時，可以直接在桌面版 app 看到整份 plan，例如講者示範的 dark mode 功能計畫
    ↳ plan mode（計畫模式）是讓 Claude 先寫出一步步的施工計畫，還不動手改程式。現在整份計畫可以直接在桌面版 app 裡看，像講者示範的『深色模式』功能計畫。
  • 10:44 可以選取 plan 裡不滿意的段落留言，留言會送回給 Claude 修改
    ↳ 看到哪段不滿意，不用重打一整段指令，直接選取那段留言，Claude 就會照你的意見改計畫。好處是還沒動工就先把方向校正好。
  • 11:14 桌面版 app 能看 pull request 裡各檔案的 diff，也能在程式碼上留言
    ↳ pull request（PR）是把一批修改送出去、請人審過再併進正式專案的申請；diff 是逐行標出哪裡新增、哪裡刪除的對照。在桌面版 app 可以看這些內容，也能直接在程式碼上留言。
  • 11:14 例如留言「Claude，解釋這一行」，Claude 就會針對那一行說明這段程式碼
    ↳ 看不懂某一行程式碼時，在那一行留言『Claude，解釋這一行』，它就會專門講那一行在做什麼。不會寫程式的人也能這樣邊看邊問。
  • 11:51 桌面版 app 底部有 GitHub 整合（講者說 Boris 也提過），可以把修正加進去
    ↳ GitHub 是存放程式碼、處理 PR 的常用網站。桌面版 app 底部有連動 GitHub 的功能，看完 diff 想補的修正可以直接加進去。講者提到 Boris 也講過這點。
  • 11:51 除了 diff 之外，也可以瀏覽專案的完整檔案
    ↳ diff 只會顯示改了哪裡；想看改動前後的整體脈絡，也可以在 app 裡翻遍專案的所有檔案。
  • 12:24 講者鼓勵大家多試用，回報 bug、提出新功能，並建議產品之後該往哪個方向走
    ↳ 這些功能還在發展中。講者希望大家多拿來用，遇到問題就回報，有想法就提出來，也可以建議產品之後該往哪個方向走。
  • 12:54 接下來講「自主性」：常見痛點是長時間的 session 卡在權限請求或下錯指令，這些事其實 Claude 自己就能處理
    ↳ session 是你和 Claude 一次連續的工作過程。任務一跑久，常常卡在等你按『允許』，或因為指令下錯而停住。講者認為這些事很多其實 Claude 自己就能處理。
  • 13:24 模型越來越強，Claude 也越來越會判斷什麼時候真的需要你介入
    ↳ 模型越來越強，越分得出哪些事真的要問人、哪些它可以自己決定，所以不用每一步都停下來等你。
  • 13:54 新的 auto mode：解決長時間執行時一直跳出「可以讀這個檔案嗎？」「可以存取這個資料夾嗎？」這類授權請求的問題
    ↳ auto mode（自動模式）要解決的是：長任務跑到一半，一直跳出『可以讀這個檔案嗎？』『可以存取這個資料夾嗎？』，你只好守在電腦前一直按同意。
  • 13:54 auto mode 靠最新模型的能力來判斷一個情況是不是破壞性的
    ↳ 它做得到，是因為最新的模型已經能看出一個動作會不會造成破壞，例如刪掉之後救不回來的東西。
  • 14:28 原本 Claude 會停下來要權限的時候，auto mode 改用 classifier 檢查兩件事：這個動作是否具破壞性（之後會不會後悔）、看起來是否像 prompt injection
    ↳ classifier（分類器）是一道自動判斷的關卡。原本要問你的時候，改由它檢查兩件事：這個動作做了會不會後悔；看起來是不是 prompt injection，也就是有人偷塞指令，想操控 Claude。
  • 14:28 兩項都沒問題，Claude 就會代你執行，不停下來，繼續跑
    ↳ 兩項檢查都過了，Claude 就直接幫你做完這一步，繼續往下跑，不會打斷你。
  • 15:00 只要有一項沒通過，Claude 會先找替代路徑，避開需要權限或具破壞性的做法；真的沒辦法才回來問你
    ↳ 只要有一項沒過，它不會硬做，也不會馬上跑來問你，而是先找別的做法避開風險；真的沒辦法，才回來問你。
  • 15:30 這呼應 Boris 講的非同步寫程式：讓 Claude 自己跑，只在真的需要時才來問你
    ↳ 整體方向是『非同步』工作：你交代完就可以去忙別的，Claude 自己跑，只有真的需要你決定時才來找你。
  • 15:30 worktree 適合多個 Claude 同時在同一個 repo 工作，避免彼此干擾、改到同樣的東西
    ↳ repo 是一個專案存放程式碼的地方。worktree 適合同時開好幾個 Claude 做同一個專案，避免它們互相干擾、改到同一個地方。
  • 16:03 worktree 是專案在獨立子目錄的一份副本，只給一個 Claude session 使用
    ↳ worktree 就是把專案另外複製一份，放在獨立的資料夾裡，一個 Claude session 用一份，各做各的，不會搶著改同一份檔案。
  • 16:03 worktree 早在 Claude 出現前就有，Claude Code 一開始也支援，但以前要自己管理多個目錄，而且工作中斷時 worktree 有點短暫易失，很難弄對
    ↳ worktree 是程式界早就有的工具，不是 Claude 發明的。以前要自己管好幾個資料夾，工作一中斷就容易亂掉，很難弄對。
  • 16:35 現在 Claude Code 原生支援 worktree：用 claude --worktree 開 session，Claude 會把 repo 複製到獨立目錄各自作業
    ↳ 現在 Claude Code 內建支援：開 session 時輸入 claude --worktree，Claude 就會自動把專案複製到獨立資料夾，在那裡工作。
  • 16:35 多個 Claude 可以在同一專案做不同功能，不會同時檢查、編輯同一批檔案
    ↳ 這樣可以讓一個 Claude 做 A 功能、另一個做 B 功能，各改各的檔案，不會同時去看、去改同一批檔案。
  • 17:05 已經在 session 裡的話，也可以直接請 Claude 幫你建 worktree
    ↳ 如果已經在 session 裡了，也不用重開，直接請 Claude 幫你建一個 worktree 就好。
  • 17:05 桌面版 app 等介面也原生支援 worktree，開新 session 時就有旗標標示會開新 worktree，不用自己管
    ↳ 在桌面版 app 開新 session 時，畫面上會標示這次會開一個新的 worktree，資料夾要怎麼管都交給它，不用你操心。
  • 17:37 auto memory 解決的痛點：每次開新 session 都像從零開始，同樣的事要一再告訴 Claude，即使有 CLAUDE.md 也常漏掉小細節
    ↳ auto memory（自動記憶）要解決的是：每次開新 session，Claude 都像失憶一樣，同樣的事要重講。CLAUDE.md 是你寫給 Claude 的專案說明檔，但小細節常常沒寫到。
  • 18:10 auto memory 會隨 session 進行自動在背後記筆記，例如你的 coding 風格、架構選擇、除錯心得，存進 memory.md
    ↳ Claude 工作時會在背後自動記筆記，像是你習慣的寫法、專案架構為什麼這樣安排、之前的 bug 是怎麼修好的，都存進 memory.md 這個檔案。
  • 18:10 不是每個 session 都會更新，Claude 會判斷哪些東西值得記下來以後用
    ↳ 它不是每次都記，而是自己判斷哪些東西以後用得上才記下來，避免筆記塞滿沒用的內容。
  • 18:41 memory.md 會和 CLAUDE.md 一起載入之後的每個新 session
    ↳ 之後每開一個新 session，memory.md 會和 CLAUDE.md 一起被讀進來，Claude 一開始就知道之前學到的事。
  • 18:41 兩者差別：CLAUDE.md 像第一天上班給 Claude 的新人手冊，memory.md 像 Claude 工作時自己記的筆記；一個是說明書，一個是筆記
    ↳ CLAUDE.md 像你在新人第一天給的工作手冊，由你來寫；memory.md 是 Claude 自己工作時記的筆記，由它慢慢累積。一個是說明書，一個是筆記。
  • 19:11 memory.md 很短，主要是指向各個具體記憶檔的索引，所以不會讓 context 變臃腫
    ↳ context 是 Claude 一次能拿來參考的內容，塞太多會拖慢速度、影響表現。memory.md 很短，主要是一份目錄，列出各份筆記放在哪，所以不會佔掉太多空間。
  • 19:11 採用漸進式探索（progressive discovery）：需要某項記憶（例如除錯記憶）時，先讀索引、找到檔案，才載入 context
    ↳ progressive discovery（漸進式探索）就是需要時才去翻：例如要除錯，先看目錄找到除錯的筆記，再把那一份讀進來，其他的先不讀。
  • 19:42 同一專案的所有 session、所有 worktree 共用同一份記憶
    ↳ 同一個專案裡，不管開了幾個 session、幾個 worktree，用的都是同一份記憶。在其中一個學到的事，其他的也知道。
  • 19:42 記憶檔不會離開你的電腦：不會推到 GitHub，也不存在雲端，只存在你的機器上
    ↳ 這些記憶檔只存在你自己的電腦裡，不會推到 GitHub，也不會存在雲端。
  • 19:42 輸入 /memory 可以查看、稽核 Claude 幫你管理的整個記憶目錄
    ↳ 輸入 /memory 可以打開整個記憶資料夾，看看 Claude 替你記了哪些東西、記得對不對。
  • 20:14 code review 是 Anthropic 開發團隊日常採用、測試有效後才做進產品的做法，會自動審查你建立的每個 PR
    ↳ code review（程式碼審查）是修改併進專案之前，先檢查有沒有問題。這個功能是 Anthropic 團隊自己天天在用、確定有效才放進產品的，會自動審查你開的每一個 PR。
  • 20:46 code review 是多 agent、多階段的流程：建立 PR 後，Claude 會派出一組 agent 分別審查 PR 的不同部分
    ↳ 它是 multi-agent（多代理）的做法。agent 是能自己執行任務的 AI 助手；這裡一次派出好幾個，分別審查 PR 的不同部分，而且分成好幾個階段。
  • 20:46 第一階段各個 agent 分工檢查不同問題，例如錯誤、bug、安全漏洞、邏輯錯誤
    ↳ 第一階段各自分工找問題：有的專抓錯誤和 bug（程式的毛病），有的找安全漏洞，有的檢查邏輯有沒有出錯。
  • 20:46 第二階段拿所有發現對照實際程式碼，確認問題真的存在，藉此更快找出錯誤
    ↳ 第二階段把找到的問題拿回實際的程式碼一一核對，確認問題真的存在、不是誤判，這樣能更快找出真正的錯誤。
📘 術語
plan mode（規劃模式）：讓 Claude 產生功能的逐步實作計畫，可以在桌面版 app 查看，也能在計畫上留言
diff（差異比對）：pull request 裡檔案的變更內容，可以在桌面版 app 查看和留言
pull request (PR)（合併請求）：字幕沒有解釋定義，只提到能看它的 diff，以及 code review 會自動審查每個 PR
auto mode（自動模式）：用 classifier 判斷動作是否具破壞性、是否像 prompt injection，都沒問題就不問你直接執行
classifier（分類器）：auto mode 用它檢查動作是否具破壞性、是否像 prompt injection
prompt injection（提示注入）：字幕描述成「有東西要注入到我的 prompt 裡」，是 auto mode 檢查的第二項
worktree（工作樹）：專案在獨立子目錄的一份副本，只給一個 Claude session 使用，避免多個 Claude 互相干擾
auto memory（自動記憶）：Claude 在 session 中自動記下 coding 風格、架構選擇、除錯心得等，存進 memory.md
CLAUDE.md（CLAUDE.md 說明檔）：比喻成第一天上班給 Claude 的新人手冊
memory.md（記憶檔）：Claude 工作時自己記的筆記，很短，主要是指向其他記憶檔的索引
progressive discovery（漸進式探索）：先讀索引、找到需要的記憶檔才載入 context，避免 context 臃腫
context（上下文）：字幕沒有解釋定義，只說 memory.md 的設計是為了不讓它變臃腫
code review（程式碼審查）：自動審查每個 PR，流程是多 agent、多階段
multi-agent（多 agent）：code review 會派出一組 agent，分別檢查錯誤、bug、漏洞、邏輯錯誤等
✏️ 小考一題

根據影片，auto mode 的 classifier 在 Claude 原本要停下來要權限時，會檢查哪兩件事？

A. 動作是否具破壞性，以及看起來是否像 prompt injectionB. 動作是否會修改檔案，以及是否需要網路連線C. 動作是否符合 CLAUDE.md 的規範，以及是否會超出 context 上限D. 動作是否會影響其他 worktree，以及是否需要推到 GitHub
看答案
答案：A。[14:28] 講者說 classifier 檢查兩件事：第一，這個動作是否具破壞性、之後會不會後悔；第二，看起來是否像 prompt injection。
